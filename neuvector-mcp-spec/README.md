# NeuVector MCP Server — implementation spec package

A complete, machine-checkable specification for building an enterprise-grade MCP
server over the SUSE NeuVector container security platform, written to be
implemented correctly by a 30B-class coding model.

**Spec version 1.0.0** · **Target NeuVector 5.6.x** · Definition of done:
`make verify` exits 0.

## How to drive `qwen3-coder:30b` through it

The single biggest failure mode for a 30B model on a project this size is context
exhaustion followed by invention. The phase structure exists to prevent that: each
phase is small enough to hold, and each ends in a gate the model cannot argue with.

### Session 0 — orientation

```
Read SPEC.md in full. Then read phases/PHASE-0-scaffold.md and do only that
phase. Report the two gate outcomes. Do not read any other phase file.
```

### Sessions 1-11 — one phase per session

Start a **fresh context** for each phase. The prompt is the same shape every time:

```
You are implementing the NeuVector MCP server, phase N.

Read, in this order:
  1. SPEC.md sections 0 (rules), <the sections that phase names>
  2. phases/PHASE-N-<name>.md
  3. only the tools/PART-X.md sections that phase names

Then implement the phase. Run its gate command. Report:
  - the exact tool count from `make spec`
  - the `make verify` result
  - any BLOCKED item you hit

Do not read other phase files. Do not start phase N+1.
```

### When a gate fails

Feed the failure back verbatim and nothing else:

```
`make verify` failed with:
<paste output>

Fix only what this output names. Do not refactor anything that passes.
```

Resist the urge to let the model "improve" passing code. Every rewrite of a
passing module is a new chance to break it.

### If the model reports `BLOCKED`

That is the spec working as designed. `BLOCKED` means the model looked for an
endpoint or a field, did not find it in the appendices, and refused to invent one.
Resolve it yourself — usually by checking a live controller — then hand back the
concrete answer. Do not tell the model to "figure it out".

## Why the spec is shaped this way

Six choices do most of the work in getting a 30B model to a correct result.

**A working core, not a description of one.** `reference/` is not pseudocode. It
is 9 modules plus 2 tool modules that were executed in a sandbox: 11 tests pass,
all 9 gate rules pass. Phase 0 copies it. The model therefore starts from working
auth, retry, error classification, the write guard and the audit middleware — the
parts it would most likely get subtly wrong — and only ever writes tools.

**A machine-checkable gate, not a review.** `scripts/verify_spec.py` introspects
the assembled server and enforces 9 rules: naming, description structure,
annotation consistency, toolset tagging, the `confirm` parameter, the endpoint
allowlist, structured output, test coverage, and registration. "Looks right" is
not an outcome the model can claim.

**An endpoint allowlist derived from source.** Appendix A was generated by
parsing `controller/api/apis.yaml` (232 operations) and `controller/rest/rest.go`
(340 registered routes). Gate rule R6 parses the `Calls <METHOD> <path>` line out
of every docstring and checks it against that list. A hallucinated endpoint fails
the build rather than failing in production.

**Phases sized to a context window.** Each phase file is under 200 lines and
names the exact sections to read. The tool contracts are split across four files
so no phase needs more than one.

**Read and write toolsets that never mix.** A toolset is entirely read or
entirely write, so `readOnlyHint` is derivable from the tag and rule R3 can check
it mechanically. `NV_READ_ONLY=true` plus a mutating toolset is a startup error,
not a silent downgrade.

**A confirmation handshake the model cannot skip.** Every mutating tool returns a
plan with a payload-bound token on the first call and only acts on the second.
The test that asserts `route.call_count == 0` on the preview call is the entire
safety model compressed into one line.

## Verified, not recalled

Everything below was established in a live sandbox on 2026-07-29, not from memory.

| Claim | How it was established |
|---|---|
| 232 documented operations, 396 schema definitions | parsed `controller/api/apis.yaml` from `neuvector/neuvector@main` |
| 340 registered routes, 112 undocumented | parsed `controller/rest/rest.go` and diffed against the Swagger paths |
| Query conventions (`f_`, `s_`, `start`, `limit`, operator degradation) | read `restParseQuery` in `controller/rest/rest.go` and the constants in `controller/api/apis.go` |
| Auth header precedence and API key format | read `restReq2User` in `controller/rest/auth.go` |
| Error codes 1-55 with their exact strings | extracted from `apis.go` constants joined to the `restErrMessage` table in `rest.go` |
| FastMCP 3.4.5 API surface | installed it and introspected `FastMCP.__init__`, `.tool()`, `.run_http_async()`, `list_tools()`, `Middleware`, `StaticTokenVerifier` |
| The reference core works | ran it: 11 tests pass, `verify_spec.py` reports 9/9 rules clean |
| openSUSE BCI Python 3.13 exists | queried the registry tag list: `3.13` → 3.13.13 |
| All 84 endpoint references in the tool contracts are valid | ran the gate's own R6 matcher over every `Calls` line: 0 violations |

Where the upstream schema does not cover a type, the tool contracts say
`BLOCKED (schema)` and give a defensive projection plus an instruction to confirm
against a live controller. Nothing is quietly guessed.

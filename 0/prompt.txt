## Exact `effect` text of the two bulk deletes

Rendered with `expected_rule_count=137` / `12`, `scope="local"`:

**`nv_delete_all_network_rules`**
&gt; Delete ALL 137 network policy rules in scope 'local' - scope 'local' means THIS cluster's own rules; federated rules pushed by a federation primary are left alone. **`nv_delete_all_admission_rules`**

## How I determined the omitempty / partial-update semantics

From apis.go, which the conventions make authoritative over apis.yaml:

```go
// Omit fields indicate that it's not modified.
type RESTPolicyRuleConfig struct {
	ID           uint32    `json:"id"`
	Comment      *string   `json:"comment,omitempty"`
	From         *string   `json:"from,omitempty"`
	To           *string   `json:"to,omitempty"`
	Ports        *string   `json:"ports,omitempty"`
	Action       *string   `json:"action,omitempty"`
	Applications *[]string `json:"applications,omitempty"`
	Disable      *bool     `json:"disable,omitempty"`
	CfgType      string    `json:"cfg_type"`
	Priority     uint32    `json:"priority,omitempty"`
}
type RESTPolicyRuleConfigData struct {
	Config    *RESTPolicyRuleConfig `json:"config"`
	Replicate bool                  `json:"replicate,omitempty"`
}
```

The struct comment states omission means "not modified" outright, and every mutable field is a pointer with `omitempty` — a nil pointer marshals to an absent key, never `null`. So absence is the "leave alone" signal, and a key present with any value (including a default) is an overwrite instruction. `id` and `cfg_type` are the two non-pointer fields and apis.yaml lists exactly those two under `required`, so `_rule_config_body` always emits them. apis.yaml agrees with apis.go on field names here; no conflict to resolve.

## Deviation from the brief, with the argument

**I did not reuse `NetworkRuleInput` / `_rule_body` for `nv_update_network_rule`.** Doing so would have produced a functionally wrong tool:

- `_rule_body` renders a `RESTPolicyRule` (the batch CONFIGURE shape), not a `RESTPolicyRuleConfig`, and is not nested under `"config"` — the wrong wire shape for this endpoint.
- `NetworkRuleInput` cannot express a partial update. `from_group`/`to_group`/`action` are required; `ports` defaults to `"any"`, `applications` to `[]`, `comment` to `""`, `disable` to `False`. Rendering it always emits every key, so a caller who only wanted to flip `action` would silently reset the rule's ports to `any` and blank its comment. That is the same class of failure as the 1.0.3 policy-mode bug, only worse — a 200 that applies changes nobody asked for.

Instead the tool takes flat optional scalars (`from_group`, `to_group`, `action`, `ports`, `applications`, `comment`, `disable`, all defaulting to `None`) and a module-local `_rule_config_body` helper writes each key explicitly. No parallel `*Input` model was created, so the "don't define parallel models" intent is honoured — there is simply no model to share. `applications=[]` is distinguished from omitted: `[]` is sent (meaning "any application"), `None` omits.

The docstring states when to use which tool: this one for partial changes to one rule; `nv_apply_network_rule_changes` when several rules must change atomically or when order matters, since only the batch tool can insert/move/delete and its `configure_rules` entries overwrite the whole rule.

## Limitation I did not paper over

`cfg_type` is hardcoded to `"user_created"`. apis.yaml's enum also allows `learned`, `ground` and `federal`, but `PATCH /v1/policy/rule/{id}` has no `scope` query parameter, and I have no offline evidence for how the controller treats a federal-rule PATCH carrying `cfg_type: user_created` (conversion? rejection? silent drop?). Rather than guess, the tool updates user-created local rules only and the docstring says learned rules are rejected with code 4. Federated single-rule updates are out of scope for P5 — flag if the coordinator wants them.

## Wire-shape findings from apis.go (5.6.0)

DLP's structs are field-for-field identical to WAF's except where noted, so the WAF template held — but three pointer/omitempty details would have been got wrong by copying WAF verbatim:

1. **`RESTDlpSensorConfig.Comment` is `*string` + `omitempty`.** Omitting means "leave unchanged"; `""` means "clear it". `nv_update_waf_sensor` sends `"comment": comment` unconditionally with a `""` default, so a WAF update that doesn't restate the comment **silently wipes it**. `RESTWafSensorConfig.Comment` is the same pointer type, so this is a live (small) bug in the shipped WAF tool — flagging it rather than touching that file. DLP's tools take `comment: str | None = None` and omit the key entirely when unset.

2. **`RESTDlpGroupConfig.Status` is `*bool` + `omitempty`.** `nv_set_waf_group` defaults `status=True` and always sends it, so binding sensors on a group where inspection was deliberately off silently re-enables it. `nv_set_dlp_group` takes `status: bool | None = None` and omits the key when unset; the plan text says which of the two applies.

3. **`RESTDlpCriteriaEntry.Context` is `omitempty` and has no documented value set for DLP** (apis.yaml refs the generic `RESTCriteriaEntry`, which documents only `key`/`value`/`op`). The input model accepts the WAF value set as an optional field and **omits `context` from the body when unset** rather than inventing a default. This is the one genuinely ambiguous field — it is not verified for DLP.

Other differences worth recording:
- **apis.yaml is wrong about `RESTDlpGroupConfig.sensors`/`replace`**: it says `RESTDlpSetting`; apis.go says `*[]RESTDlpConfig` (`{name, action, comment?}`). apis.go wins per conventions, so `replace` sends `{name, action}` — same as the live-verified WAF shape.
- **`RESTDlpSetting` carries `predefine`, which `RESTWafSetting` does not** — DLP ships predefined sensors, so `DlpGroupSensor` exposes `predefined`.
- `RESTDlpRule.id`/`cfg_type` are controller-assigned (ids from `MinDlpRuleID` 20000) and are not sent; `cfg_type: "user_created"` goes on the config on create only, not on PATCH (mirrors WAF).
- `GET /v1/dlp/group` documents **no `scope` parameter** (WAF's does), so none is sent and paging is client-side. Asserted by a test.
- Added real controller limits as constants from apis.go and enforce them pre-guard via `ValidationError_`: 16 patterns/rule, 512 chars/pattern, 1024 chars total/rule, 256-char names and comment.

## `NV_ALLOWED_NAMESPACES` gap on `nv_apply_system_request`

`POST /v1/system/request` carries no namespace anywhere in its body, so `authorise_write(namespace=None)` — the allowlist check in `guard.py:90` never fires. **A server configured with `NV_ALLOWED_NAMESPACES` still applies this to every namespace, including ones outside the allowlist.** Stated in three places: the docstring (own paragraph, in caps), the guard `effect` text, and a test (`test_apply_system_request_ignores_namespace_allowlist`) that asserts `route.call_count == 1` under a `staging`-only allowlist so the gap is a pinned, visible property rather than an oversight. Docstring opens by naming `nv_set_service_mode` as the scoped alternative; the Protect `effect` spells out that blocking starts across every namespace the moment the call returns and breaks apps never observed in Discover.

Sub-requests exposed as explicit named params (from apis.go `RESTSystemRequest`/`RESTUnquarReq`), not a free-form dict: `policy_mode`, `baseline_profile`, `unquarantine` (bool switch), `unquarantine_group`, `unquarantine_response_rule_id`. Filters without `unquarantine=true` are rejected; an all-empty request is rejected.

## Quarantine: not duplicated, but the wire forces it

I did **not** add a quarantine feature — but I could not avoid the field. apis.go `RESTWorkloadConfig.Quarantine` is a plain `bool` with **no `omitempty`**, and apis.yaml lists `quarantine` under `required`. apis.yaml binds `PATCH /v1/workload/{id}` to `RESTWorkloadConfigData`, which wraps that non-pointer type. (apis.go also has a pointer-valued `RESTWorkloadConfigCfgData`, but nothing in apis.yaml references it.) So **this route has no "leave quarantine alone"** — an omitted key decodes as `false`, and a naive wire-mode PATCH would silently release a quarantined container.

Handling: `quarantine` is a **required** argument documented as the state the call *asserts*, to be echoed back from `nv_get_workload`; and `wire` is required via `ValidationError_` pointing at `nv_quarantine_workload`, so a quarantine-only call is refused and the two tools cannot become redundant paths. No pre-read (that would be a controller call before step 3), so the plan labels it a caller assertion — same precedent as `expected_rule_count` in P5.

## Findings you need to decide on

**1. `POST /v1/file/config` is NOT an export — the brief is wrong about this.** apis.yaml 5.6.0 declares `GET /v1/file/config` = "Download a configure file" and `POST /v1/file/config` = "Upload configure file", `consumes: multipart/form-data`, `formData` file `configuration`. POSTing there to "export" would trigger a **whole-cluster configuration import**. I implemented `kind="all"` as the GET (also in `spec_endpoints.json` `documented`) and there is a regression test asserting the POST route is never called. I did **not** implement a whole-cluster import: multipart transport is unverified and it is the single most destructive call in the API.

**2. The Git PAT committer-email field name conflicts across sources.** apis.go tags it `personal_access_token_email`; apis.yaml *and* Appendix B both document `personal_access_token_committer_email`. Per the conventions rule (apis.go wins) I send the apis.go name — the yaml name would be a silently-dropped field behind a 200, i.e. the exact 1.0.3 failure. Flagging because two of three sources disagree with what I shipped.

**3. Git PAT is covered.** `personal_access_token` is already in `SECRET_FIELDS` (models.py:231, cited to `RESTRemoteRepo_GitHubConfig`). No change needed. My tools use the two-payload rule (`redact_secrets` for guard + result), and a test asserts the literal token appears nowhere in the serialised plan or outcome. **However**: `RESTImportTask.temp_token` is a resume bearer token and is *not* in `SECRET_FIELDS` — I drop it from the projection rather than surfacing it, but you may want it added.

## `request_text` design

Extracted the existing retry/relogin/classify loop verbatim into `NeuVectorClient._send`, which returns the raw `httpx.Response`. `request` is now `_send(...)` + `_safe_json(response) or {}` — byte-identical behaviour, and all 64 client tests pass unchanged. Two new public methods share that path: `request_text` (returns `response.text` in full, never truncated) and `send_document` (sends a raw UTF-8 body with `Content-Type: text/plain; charset=utf-8`, returns parsed JSON). `_send` gained `content=` and `extra_headers=`, both defaulting to None, so no existing call site changes shape.

## Export size cap

Default `max_characters=20000` (~5k tokens), bounds 1000–200000. When clipped, `controller_response.truncated=true` plus a hint naming the real length and that a truncated document is not importable. `kind="all"` always sets `truncated=true`/`withheld=true` and returns `yaml: ""`.

**Deviation from the brief:** `truncated` lives inside `controller_response` (a declared field of `WriteOutcome`), not as a top-level field of a new output model. Reason: the guard returns a `WriteOutcome`, and the five-step rule says return the plan *verbatim*; a subclass return type would force reconstructing the plan. It is still machine-readable structured output. Change it if you'd rather I subclass.

## What redaction does and does not catch — exactly

No YAML parser is available (`pyproject.toml` deps are fastmcp/httpx/pydantic/structlog only), so `redact_yaml_secrets` is a **line filter**, not a parser.

**Catches:** the seven `SECRET_FIELDS` names as block-mapping keys at any indentation, including as the first key of a sequence item (`- password: x`), with plain, quoted, or block-scalar values — and for `|`/`&gt;` it drops the whole indented block, so a multi-line `json_key` doesn't survive its header.

**Does NOT catch** (each pinned by a test in `test_redactor_documented_blind_spots_are_real`, so the claim can't drift):
- flow style — `creds: {password: hunter2}` passes through intact;
- a token embedded in the *value* of an innocuous key — `url: https://hooks.example/T00/B00/s3cr3t` is returned verbatim;
- any credential under a key name not in `SECRET_FIELDS`, including anything a future controller adds;
- secrets inside free-text `comment`/`description`;
- values the controller already emitted encrypted or base64-wrapped.

Because a full cluster export is exactly the document where the blind spots bite (webhook URLs with tokens in the path, directory-server secrets), **`kind="all"` refuses to return the body**. It reports size, line count, and a count of credential key names detected — names and counts only, never values. Narrow kinds return redacted YAML with `credential_keys_found` so "0 found" is distinguishable from "redaction didn't run". `nv_import_config` also *rejects* a document still containing the `***` sentinel, so a round-trip can't store `'***'` as a live credential.

## Import transport: documented shape, NOT verified

apis.yaml lists `consumes: ["application/json", "text/plain; charset=utf-8"]` with `in: body, schema: {type: string}` for all seven `/config` routes — a raw body, not multipart (multipart appears only on `POST /v1/file/config`, which I excluded). I send `text/plain; charset=utf-8`. **Not verified against a controller.** Also unverified: whether an empty `names`/`ids` list means "everything" on the export endpoints (documented nowhere), and whether a partial `github_configuration` on the PATCH merges or replaces — both stated plainly in the tool descriptions and in the confirmation `effect`.

## Deviation you should rule on

`nv_get_import_status` is tagged **`policy_read`**, not `system_write`. CONVENTIONS is explicit that "a toolset is never mixed — read tools and write tools never share a tag", and R3/R5 would force `readOnlyHint=False` + a `confirm` parameter on a GET poll. Move it if you disagree.

- Whole-cluster import (`POST /v1/file/config`, multipart) — see finding 1.
- `remote_export_options` on the export bodies (pushes to a Git repo instead of returning YAML; changes the response to `RESTRemoteExportData` JSON) — out of brief scope.
